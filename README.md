# 東京租屋比價

東京租屋的痛點不是「找不到房」，是**無法比較**。

房源分散在各家自營網站，每家只放自己的房子；費用結構每家寫法不同——禮金、敷金、管理費、共益費、保証会社料、含不含水電、附不附傢俱。「月租 55,000」和「月租 62,000 含水電免禮金」根本沒辦法直接比。再加上幾乎全是日文，動線又亂。

這個站把各來源的房源抓下來、正規化成同一套欄位，以**實質月成本**與**初期費用**為主軸做跨站比較，挑到房後連回原站承租。

定位是導流型比價站：不承接交易、不取代原站，每一筆都連回去。

## 快速開始

```bash
npm install
npm test                    # 109 個測試
npm run crawl               # 抓取（ひつじ全量約 60 分鐘）
npm run build:data          # 產生網站用的欄式 JSON（含驗證閘門）
npm run dev                 # 本機開站
```

只想先看畫面、不想等抓取：

```bash
npm run crawl -- --limit 40 && npm run build:data && npm run dev
```

## 最高原則：不虛構任何數值

使用者的第一原則是「抓不到就說抓不到，絕不編一個數字」。這件事沒有靠慣例維持，而是**架構層強制**：

**1. 金額不是裸 number。** `Yen` 是物件包裝，因為 JavaScript 裡 `null + 5 === 5`、`Math.min(null, 100) === 0`——用 `number | null` 表示「不知道」，任何一次忘記檢查的算術都會靜默地把未知變成 0。包成物件後裸的 `a + b` 直接編譯失敗：

```
error TS2365: Operator '+' cannot be applied to types 'Yen' and 'Yen'.
```

**2. 沒有值的時候「根本沒有 `.v` 這個屬性」。** `Field<T>` 是判別式聯集，未檢查就存取是編譯錯誤：

```
error TS2339: Property 'v' does not exist on type 'Field<Yen>'.
```

就算繞過型別，執行期得到的是 `undefined + 5 = NaN`（大聲失敗），而不是 `null + 5 = 5`（靜默造假）。

**3. `sumYen` 是全專案唯一能加總金額的入口**，且強制回傳 `missing` 清單——讓「算了但不知道漏什麼」在型別上不存在。

**4. 建置期閘門。** `npm run build:data` 在寫出任何檔案**之前**驗證，任一條失敗就 exit 非零、不產出檔案：

- 金額為 0 但無依據（`basis='unstated'` 且無原文）→ 失敗
- 宣稱 `measured` 卻沒有 `srcText` 出處 → 失敗
- 產出 `capabilities.provides` 之外的欄位 → 失敗

**5. 排序分區，缺值不混算。** A 完整可比／B 僅有下限／C 資料不足，三區互不排序。缺仲介費的物件永遠在 B 區，資料完整的永遠在 A 區——缺值是降級，不是取得排序優勢。永遠不做「缺值當 0 混排」或「直接刪掉缺值物件」。

## 費用模型的兩個關鍵決定

**敷金不是成本，是押金。** 把敷金整筆算進「初期費用」再排序，會讓「敷2礼0」看起來比「敷0礼1」貴，但實際沉沒成本相反。所以拆成兩個指標：

| 指標 | 包含 |
|---|---|
| 初期現金需求 | 敷金＋礼金＋仲介＋保証初回＋保険＋鍵交換＋前家賃＋日割家賃 |
| 初期沉沒成本 | 礼金＋**敷引/償却**＋仲介＋保証初回＋保険＋鍵交換＋清掃費 |

敷金 > 0 但敷引未知時，沉沒成本標為下界並顯示「敷金可能有部分不退，原站未載明」。

**月額 = 賃料＋管理費/共益費。** 水電不算進完整性判定——日本幾乎沒有任何網站逐物件報價水電，拿它判定完整性會讓每一筆都落入「僅有下限」，一個永遠相同的訊號不帶任何資訊，反而淹沒真正該被標示的缺項。水電的不確定性改由 `utilitiesBasis` 標籤、篩選器、以及「結果集混合兩種基準」的警示橫幅承擔。

## 已查證的法源與基準

| 敷引き特約 | 原則有效，但相對賃料過高時依消契法10条無效 | 最高裁 平成23.3.24 民集65巻2号903頁 |

## 架構

```
packages/schema/      Field<T> 判別式聯集、Yen 名義型別、Building+Unit 模型、不變式
packages/jp-parse/    日文解析：金額、月數、面積、帖、徒歩、間取り、契約條件
packages/cost-model/  費用比較：初期現金 vs 沉沒成本、A/B/C 分區、日割家賃
crawler/src/          transport（http/browser/file）、robots、RSC payload、健康檢查
crawler/sources/*/    每來源只需實作 extract；fixtures 是凍結的真實頁面快照
web/                  Vite + React，欄式 JSON + 瀏覽器端掃描
```

爬蟲與網站**完全分離**：爬蟲產物是 `data/normalized/*.ndjson`（進 git，一行一棟，`git diff` 讀得懂價格變動），網站只是讀 JSON 的靜態頁。

**為什麼不用搜尋索引函式庫**：實測 8 條件掃描 5,000 筆 0.01 ms、30,000 筆 0.15 ms。引入依賴去換一個已經是 0.15 ms 的東西不划算。

**為什麼是欄式 JSON**：實測 5,000 筆 × 27 欄，列物件 363 KB gzip、列元組 311 KB、欄式 254 KB。Int32 二進位反而打不贏（小整數的十進位表示比固定 4 bytes 省，gzip 又吃得很好）。門檻：單檔 ≤ 10,000 筆 / ≤ 500 KB gzip，超過才啟動分片。

## 合規

- **不繞過任何 bot 防護或人機驗證。** 出現需要點選的驗證畫面就停手交還使用者。
- 每次執行都**重新抓取並解析 robots.txt**，絕不硬編碼查證結果；sha256 變動就停掉該來源等人重新檢視。
- 每站設請求間隔（預設 3 秒，單站單執行緒），並取 robots.txt `Crawl-delay` 的較大值。
- User-Agent 標明用途與聯絡方式。
- 只儲存事實性欄位與原文短片段；圖片只引用原站 URL，不轉存。
- 每筆房源都顯示來源站名與「前往原站」按鈕。
- 每個 adapter 帶 `legal.enabled` 開關，可隨時關閉單一來源。

## 新增一個來源

```
1. cp -r crawler/sources/_template crawler/sources/{new}
2. 填 manifest（robots 實測結果、crawlDelayMs、legal、capabilities）
3. 寫 discover（多數是 sitemap 過濾）
4. 抓 10 頁存進 fixtures/
5. 寫 extract，跑 npm test 直到綠
6. 決定 capabilities.neverProvides（來源根本沒有的欄位，
   宣告出來健康檢查才不會產生永遠 0% 的假警報）
```

所有日文解析都在 `packages/jp-parse`，來源只寫「哪段文字對應哪個欄位」，不寫「文字怎麼變數字」。

## 健康檢查

每次抓取產出 `data/health/latest.md`（進 git，`git diff` 就看得到變化）。

告警需要**絕對差 + 相對比 + 小樣本護欄**三者同時成立：

```
RED    當 n ≥ 30 且 fill < baseline − 0.15 且 fill < baseline × 0.60
YELLOW 當 n ≥ 30 且 fill < baseline − 0.08
```

只用相對比會對低填充率欄位過度敏感；只用絕對差對高填充率欄位不夠敏感。基線取最近 5 次執行的**中位數**，一次異常不會污染基線。

填充率監控抓得到「來源改版導致某欄位全空」，但抓不到「把 1ヶ月 解析成 1 円」這種值全錯而填充率仍 100% 的故障——後者靠 `fixtures/` 的黃金測試。兩者互補，缺一不可。
